**Date:** 2026-03-30

## 1. Product Statement

`403Forbidden` — это письменный roleplay-сайт в мрачной cyberpunk-антиутопической эстетике, объединяющий форумное общение, совместное письмо через `arcs`, world-энциклопедию и системные игровые слои в одну связанную платформу.

Проект не равен просто форуму, просто ficbook-площадке или просто лорной вики.  
Его суть — в связке:

- форум как социальная точка входа;
- `arcs` как основное пространство непосредственного геймплея;
- `world` как справочник и канал погружения в сеттинг;
- terminal + shell как основа интерфейсной идентичности.

## 2. Core Vision

### 2.1. Что должен чувствовать пользователь

Пользователь должен чувствовать, что:

- он получил доступ к скрытой системе;
- перед ним не обычный сайт, а портал в другой мир;
- он не просто читатель, а потенциальный игрок-персонаж;
- внутри платформы можно проживать историю, развивать героя и взаимодействовать с другими игроками в общем мире.

### 2.2. Что проект должен давать

Проект должен позволять:

- общаться в форумной среде;
- знакомиться с миром и сеттингом;
- пройти character gate и стать полноценным игроком;
- участвовать в совместном письме и создавать истории;
- развивать профиль и присутствие в системе;
- в будущем пользоваться полноценным коммуникационным слоем через `PAGER 03`.

### 2.3. Что делает проект особенным

Ключевое отличие проекта от обычного форума:

- более зрелая система совместного письма;
- более сильный атмосферный интерфейс;
- гейтнутый вход в полноценную игру через одобрение персонажа;
- интеграция социальных, игровых и worldbuilding-слоев в одну систему.

## 4. UX Layer Model

### 4.1. Terminal Layer

Terminal — это всегда присутствующий фон и фундамент системы.

Его смысл:

- черный полноэкранный слой;
- минимальный лог/системный вывод;
- ощущение активной terminal session;
- возможность ввести простые команды;
- атмосферный мост в остальные части проекта.

Примеры intended behavior:

- `-shell` открывает shell;
- `-world` открывает world/archive-like layer.

Terminal не обязан быть сложным функционально.  
Его задача — давать ощущение входа, напряжения, тайного канала и системного интерфейса.

### 4.2. Shell Layer

Shell — это основная интерактивная программа проекта.

Его свойства:

- выезжает справа;
- живет поверх terminal;
- занимает примерно `66%` ширины экрана;
- внутри него происходит `99%` основного интерактива;
- при переходах должен ощущаться как единая живая программа, а не как обычные перезагрузки сайта.

Shell содержит:

- forum;
- arcs;
- users;
- notifications;
- profile-related screens;
- shop/inventory;
- позже pager.

### 4.3. World Layer

`World` сознательно не обязан жить внутри shell.

Он должен восприниматься как:

- отдельный архивный слой;
- справочник мира;
- будто пользователь вошел в другую директорию системы;
- полноэкранный black-background experience, а не просто очередная страница внутри shell.

### 5.1. Canon names

- `arcs` — каноничное продуктовое имя игрового writing-layer.
- `users` — каноничное продуктовое имя списка пользователей.
- `pager` — каноничное имя личного и системного коммуникационного слоя.

### 5.3. Character terms

- `character application` — полная анкета персонажа на рассмотрение.
- `character profile` — отображаемое представление персонажа после approval.

## 6. User Roles

### 6.1. GUEST

Незалогиненный пользователь.

Должен:

- видеть атмосферный вход;
- иметь доступ к части публичной информации;
- знакомиться с проектом.

### 6.2. RESTRICTED

Залогиненный пользователь без одобренного персонажа.

Это промежуточная роль между “просто зарегистрированным” и полноценным игроком.

### 6.3. PLAYER

Пользователь с хотя бы одной одобренной анкетой персонажа.

Это полноценный игровой участник сайта.

### 6.4. ADMIN

Администратор с правом ручной модерации, утверждения персонажей, управления частью системных и контентных слоев.

## 7. Access Model

### 7.1. Character Gate

Character approval — это не случайный MVP-хак, а важный переходный механизм.

Его продуктовая роль:

- переводить пользователя из `RESTRICTED` в `PLAYER`;
- поддерживать ощущение вхождения в закрытую среду;
- отсеивать прямой доступ к полноценному roleplay без подготовки.

### 7.2. Restricted access

`RESTRICTED` пользователь должен иметь возможность:

- общаться во вступительных и help-зонах форума;
- читать `world`;
- читать публичные арки других игроков в view-only режиме;
- знакомиться с системой.

`RESTRICTED` пользователь не должен полноценно участвовать в игровом процессе, пока не прошел approval.

### 7.3. Player access

`PLAYER` получает доступ ко всему, что недоступно restricted-user, включая:

- полноценное участие в арках;
- создание арок;
- расширенный игровой и социальный функционал.

### 7.4. Access Matrix Reference

Текущая формальная truth-модель доступа по `arcs` зафиксирована отдельно в:

- read access;

## 9. Arcs Product Model

### 9.1. What an Arc is

Арка — это продуктовая форма письменной roleplay-игры.

Структура:

- одна арка;
- внутри множество глав;
- внутри каждой главы множество постов;
- длина постов может быть от нескольких предложений до тысяч слов.

### 9.2. Arc ownership and creation

Арки могут создавать только полноценные игроки.

### 9.3. Arc visibility

Арки должны поддерживать как минимум два режима:

- публичные;
- приватные.

Публичные арки:

- доступны для чтения restricted-user и player-user;
- в restricted-режиме должны оставаться view-only.

Приватные арки:

- доступны только тем, кому автор дал доступ;
- не должны выдавать очки, пока остаются приватными.

Публичные арки:

- доступны для более широкого чтения;
- могут участвовать в reward/discovery logic.

### 9.4. Desired arc controls

В перспективе арки должны получить гибкие настройки:

- минимальный порог слов для поста;
- полностью свободный режим длины поста;
- пошаговый режим публикации постов;
- свободный порядок публикации;
- schedule publishing для глав;
- возможность анонсировать будущую публикацию главы.

### 9.5. Discovery direction

`Arcs` должны развиваться как полноценный discovery-layer, а не просто список “книг”.

Перспективные секции:

- recent;
- trending;
- search;
- continue reading;
- scheduled/release-like announcements;
- curated visibility.

## 12. Design Locks

### 12.1. Hard locks

1. Полноэкранный черный terminal background.
2. Shell, выезжающий справа и занимающий около `66%` экрана.
3. Асимметричная композиция terminal + shell.
4. В `arcs` / `chapters` допустим split-layout, помогающий удерживать текст ближе к центру чтения.
5. При уменьшении ширины экрана в первую очередь жертвуется видимый терминал слева, затем правый rail, приоритет остается у основного контента.

### 12.2. Soft locks

- ощущение system UI / neo-militarism / brutalism / minimalism;
- shell должен восприниматься как отдельная программа;
- переходы внутри shell должны быть как можно более плавными и “бесшовными”.

### 12.3. Canon profile route

Каноничный редактируемый профильный маршрут:

- `/profile/settings`

Старые пути могут существовать только как alias/redirect.

### 12.4. Known weak zone

Mobile adaptation сейчас не является зрелой и не должна считаться решенной частью дизайна.

Решение:

## 17. Final Working Summary

`403Forbidden` — это связанная roleplay-платформа, в которой:

- terminal создает вход и атмосферу;
- shell создает основное системное пространство;
- forum ведет в сообщество;
- arcs дают главный игровой письменный опыт;
- world строит канон и погружение;

На текущем этапе главный фокус — не новые фичи любой ценой, а наведение архитектурной зрелости, чтобы дальнейшее развитие проекта происходило из сильного и устойчивого основания.
