# 403Forbidden — Engineering Canon v1

**Date:** 2026-04-05  
**Status:** active engineering canon  
**Purpose:** зафиксировать, как проект должен проектироваться и развиваться дальше с точки зрения технического лидера, уже после первого большого рефакторинга и initial performance wave.

---

## 1. Strategic Reading Of The Product

`403Forbidden` должен ощущаться не как обычный сайт с разделами, а как большая вымышленная цифровая система внутри браузера.

Главное обещание проекта пользователю в простой форме:

**ты входишь не на форум, а в работающую внутреннюю сеть живого мира, где общение быстрое, письмо серьёзное, а интерфейс ощущается как программа, а не набор страниц.**

Это означает:

- `forum` — не побочный модуль, а самая живая массовая зона общения;
- `arcs` — не просто редактор историй, а основная gameplay-среда;
- `shell` — не декоративный layout, а core interaction model;
- `world` — не обязан быть тяжёлым по функционалу, но обязан усиливать ощущение мира;
- `pager` — не ещё одна вкладка, а будущая нервная система личной и системной коммуникации.

---

## 2. Product Priority Truth

На текущем этапе приоритеты должны читаться так:

1. **надёжность и зрелость системы**
2. **forum как high-traffic social layer**
3. **writer loop как главный gameplay path**
4. **shell как безшовная программа**
5. **world и pager как следующие продуктовые усилители**

Если решение улучшает один слой, но ломает эту иерархию, решение неверное.

---

## 3. Canon Quality Bar

Любое новое решение должно стремиться одновременно к четырём качествам:

- **быстрота**
- **надёжность**
- **ясность**
- **атмосфера**

Проект нельзя развивать только как красивый UI, и нельзя развивать только как сухую backend-систему.

Правильный результат здесь всегда двойной:

- интерфейс должен ощущаться цельным и необычным;
- внутренняя инженерная форма должна быть скучно профессиональной.

---

## 4. Canon Module Roles

## 4.1. Forum

`Forum` — главный high-traffic social layer.

Канон:

- чтение тредов должно быть дешёвым и мягким;
- новые ответы должны ощущаться быстрыми;
- moderation и control flows должны быть заложены заранее;
- модель треда должна проектироваться как поток с большим числом коротких сообщений.

`Forum` нужно оптимизировать как массовый и частый path, а не как редкий контентный экран.

## 4.2. Arcs

`Arcs` — gameplay layer и ядро уникальности проекта.

Канон:

- write flow надёжнее, чем быстрое впечатление любой ценой;
- drafts и content safety важнее красивой, но хрупкой интерактивности;
- chapter posts — это литературный игровой поток, а не casual comment feed;
- каждый read/write path в `arcs` должен уважать, что это ценнейший пользовательский контент.

## 4.3. Shell

`Shell` — это программа.

Канон:

- переходы внутри shell должны ощущаться максимально безшовными;
- shell не должен вести себя как набор полных page-reloads в общем layout;
- header/mask/sticky geometry должны оставаться централизованными;
- любые локальные spacer/offset решения считаются smell, пока не доказано обратное.

## 4.4. World

`World` — атмосферный и справочный слой.

Канон:

- он не обязан быть самым технически сложным;
- но он обязан усиливать ощущение мира и сеттинга;
- он должен работать как архив и reference space, а не как случайная текстовая страница.

## 4.5. Pager

`Pager` — будущая системная коммуникационная шина.

Первая зрелая версия должна совмещать:

- system inbox
- admin/system notices
- personal messages
- RP invites / relationship flows
- status/approval communication

Но по роли это не “ещё один центр ленты”, а тихий, интимный, очень полезный коммуникационный слой.

---

## 5. Engineering Smells

Ниже — вещи, которые в этом проекте должны считаться smell почти по умолчанию:

- page или route, в котором одновременно живут transport, business logic и heavy shaping
- server page, которая напрямую проектирует себе доступ к БД без service/view-model слоя
- UI-компонент, который одновременно рендерит, fetch’ит, синхронизируется по realtime и хранит много локального workflow-state
- duplicated API contracts для одного и того же пользовательского смысла
- лишние identity hops на hot path
- client-side “repair fetch” как обязательный путь там, где сервер уже мог отдать нужный payload
- ручные geometry offsets в shell/layout там, где должен быть каноничный metrics слой
- “временные” special-case решения без явной фиксации, почему они special-case

---

## 6. Intentional Special Cases

Некоторые special-case решения допустимы и не должны автоматически считаться плохими:

- edit locks
- signed uploads
- SSE / stream routes
- auth framework boundary
- external file transfer flows

Но каждое такое место должно удовлетворять двум требованиям:

1. быть реально особым по природе;
2. быть изолированным, а не размазанным по проекту.

---

## 7. Performance Truth

Главный performance-фокус проекта сейчас:

- `forum` — массовое общение и высокая частота сообщений;
- `chapter` — самый ценный gameplay read/write path;
- `shell` — perceived seamlessness;
- `notifications/presence` — incidental traffic discipline.

Оптимизировать нужно не всё подряд, а в первую очередь то, что влияет на:

- читабельность длинных тредов;
- perceived speed reply/post actions;
- надёжность writer flow;
- фоновые сетевые расходы;
- ощущение shell как живой программы.

---

## 8. Testing And Hardening Truth

Следующая зрелая инженерная стадия проекта должна включать:

- smoke tests для главных пользовательских потоков;
- performance baselines;
- query visibility;
- anti-regression discipline;
- release checklist.

Без этого проект уже будет развиваться хуже, даже если код сам по себе хороший.

## 8.1. Prisma Change Discipline

Любое изменение `prisma/schema.prisma` должно считаться не просто code change, а runtime contract change.

Минимальный канон после Prisma schema changes:

- `prisma generate`
- `next typegen`
- `typecheck`
- restart running `next dev`

Причина простая:

- типы и generated client могут уже быть обновлены;
- но живой dev runtime всё ещё может обслуживать запросы старым Prisma bundle;
- это создаёт ложные runtime regressions вида “Unknown argument”, даже когда schema и client уже правильные.

В проекте для этого есть каноничный шаг:

- `pnpm run schema:refresh`

---

## 9. Decision Rule

Если в будущем возникнет спор “что делать дальше”, решение должно проверяться тремя вопросами:

1. Это делает проект надёжнее как систему?
2. Это усиливает `forum`, `writer core` или `shell` как ключевые зоны продукта?
3. Это приближает опыт к ощущению большой, цельной, профессиональной внутриигровой цифровой сети?

Если ответ на все три вопроса “нет” или “не очень”, это не приоритет.
